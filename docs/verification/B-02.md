## Review response

Both findings against `456cd2b` were valid. Missing-migration protection did not
disable SQLite's separate default corruption/deletion path, so the original assurance
that failed storage initialization always retained files was too broad. The original
relaunch comparison could also pass after database loss by recreating deterministic
built-ins. Its successful run established catalogue availability, not original-row
survival. The corrections and stronger evidence below supersede those earlier claims.

- `PreservingOpenHelperFactory` forwards Room's ordinary lifecycle callbacks, replaces
  the destructive corruption handler and explicitly sets `allowDataLossOnRecovery=false`.
  Its corruption callback raises a non-SQLite failure without delegating, closing,
  checkpointing, deleting, renaming or logging the database/sidecars. The failure reaches
  Home's error/retry state. UI wording now says automatic reset is disabled instead of
  promising that already damaged content remains intact.
- `HomeCatalogueTest` corrupts only an isolated seeded fixture's header. Real SQLite
  open invokes the preserving callback (confirmed by its specific exception), Home
  reports failure, and retry leaves the damaged main file byte-for-byte unchanged.
  `CorruptionCallbackTest` captures the callback installed by the production factory,
  rejects all database calls and verifies exact main/WAL/SHM/journal fixture bytes and
  disabled lossy recovery. Sidecar evidence is callback-level; it is not a claim that
  arbitrary filesystem/hardware corruption can be recovered.
- Relaunch phases now use a separate synthetic database with a custom sentinel and
  modified/archived built-in metadata. Verification reads raw DAO rows **before**
  invoking any seeding, then checks that reseeding preserves the same snapshot. The
  negative test deletes only its isolated database while retaining the preference
  snapshot and proves verification fails without reseeding. CI selects the phase
  method explicitly so the negative regression also remains in the complete suite.
- A32 airplane-mode suite: **17 passed**, zero failures/errors/skips. The strengthened
  seed/force-stop/cold-launch/verify sequence also passed (one test in each phase).
  Original airplane-mode setting 0 restored. Current-head CI is linked from PR #28;
  the older CI runs below describe the pre-review baseline only.

No schema/dependency/toolchain changes, repair/export UX, B-03 or other later feature
is included in these corrections. The default callback behaviour is documented by
[AndroidX](https://developer.android.com/reference/androidx/sqlite/db/SupportSQLiteOpenHelper.Callback#onCorruption(androidx.sqlite.db.SupportSQLiteDatabase));
the resolved Room 2.8.5 / SQLite 2.6.2 callback and recovery wiring was inspected.

## Schema and architecture decisions

- Exactly one `exercises` application table. Text UUID primary key; all columns
  non-null except catalogue version (null only for custom origin at the model boundary).
  Duplicate labels are allowed; names are not keys. No unused relationships, routines,
  substitution table, settings or history graph is introduced.
- Domain model validates canonical UUIDs, required text, unique nonempty tags and
  origin/version pairs. SQLite enforces primary-key uniqueness and NOT NULL. Tag lists
  use a validated delimiter encoding; enum names are stable schema-v1 tokens. No raw
  metadata CHECK/trigger schema outside Room's exported model is claimed.
- Manual application composition owns one lazy Room/repository instance. ViewModel
  invokes suspend seeding; Compose renders immutable loading/error state and retry.
  Repository reads prepare their own catalogue, so future callers do not depend on Home.
  No main-thread database queries or destructive fallback. KDoc and API overview updated.
- All seed changes are transactional. Custom identity collision aborts and rolls back
  earlier inserts. Existing built-in rows are never replaced, including edited labels
  and archived flags. Future catalogue updates require explicit compatibility policy;
  no update engine/custom editor/history feature is implemented now.
- B-01 had no database, so no version-0 migration exists. v1 is the first future
  migration fixture. Unsupported database-version testing proves the original six rows
  and version remain intact after rejected open; full recovery hardening remains B-07.
- Existing toolchain pins retained, including actual merged AGP 9.5.0 (the B-01 report
  and Development table had described 9.3.1). New stable Room 2.8.5 and KSP 2.3.13.
  Serialization runtime BOM 1.12.0 is justified by the observed app/test mismatch below;
  Kotlin/compiler/serialization compiler plugin remain 2.4.21. Sources and rationale
  are linked in [Development](../DEVELOPMENT.md) and the catalogue document.
