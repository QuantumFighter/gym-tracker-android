## Migration and transaction review

Schema v4 identity: `be1d62d4bfbbf3c30d2bd94267ccbdff`.
`MIGRATION_3_4` only adds lifecycle fields and exercise status.
Existing statuses derive from the existence of recorded sets;
no original field, set, template or relationship is rewritten/deleted. The fixture
compares catalogue, programs/routines/targets, cursor and complete active-session
graph. `foreign_key_check` is empty and `integrity_check` returns `ok`.
Production retains every earlier migration and the preserving corruption helper.
The existing unsupported-future-version regression now uses v5, and the interrupted
v1 migration fixture includes the v3→v4 path so its injected failure is still reached.

All authoritative writes serialize through Room transactions. Finish reads its
specific session before doing anything; a FINISHED session returns unchanged.
For a first Finish, every status/time/cursor write and reference removal is in the
same transaction. The failure-at-last-write test proves rollback of earlier writes.
Save Set reads/validates RECORDING state and writes its set plus Partial state in
one transaction. Corrections validate state/identity/values, compare the original
saved version and update the same row; concurrent stale corrections cannot silently
overwrite the first. Corrections do not insert, renumber or restart rest.
Finalised sessions have no public mutation operation. Identical committed Save UUID
retries can return a receipt without changing history; changed UUID payloads reject.

New sessions snapshot exact source membership lineage. Migrated B-04 sessions resolve
their preserved routine within the source program, preferring its selected matching
membership; existing B-03 routines are distinct. No template foreign key can delete
session snapshots. History is reconstructed entirely from session-owned records.
