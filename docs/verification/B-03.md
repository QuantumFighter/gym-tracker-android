## Review correction: Programs observer recovery

The review of `d8d6cc0` identified one non-blocking recovery defect: after a
successful load, an observer failure retained the catalogue but hid Retry because
its visibility depended on the catalogue being empty. The terminated observer
could leave Programs stale even after storage recovered. This finding was valid.

Loading failures now have a separate `loadFailed` state from validation/save
errors. Retry is visible for any loading/observation failure, including one after
the catalogue has populated. A tracked observation Job prevents another collector
from starting while the existing one is active; retry recollects the repository's
cold Room flow after failure. Draft names, occurrences, targets and cached values
are retained. Save/validation messages cannot hide a loading failure or trigger a
storage retry in a healthy screen. There is no database/schema/dependency change.

`ProgramsRecoveryTest` adds two focused Compose/ViewModel/Room regressions:

- Inject an observer exception after a successful real Room emission; verify Retry
  remains visible with the populated catalogue, saved data is unchanged, and a
  populated routine draft survives. A program committed while the observer is down
  appears after clicking Retry. Repeated load calls keep one active collector, and
  a further write appears through the resumed live observation.
- Recover from an initial observation failure, then reject a blank program name
  without presenting an unrelated storage Retry action.

Executed after this correction: offline application/test APK builds, Android lint
(No issues found), Spotless, all 10 JVM tests and Dokka passed. The full A32 suite
reported `OK (30 tests)` in airplane mode, including both recovery regressions and

## Implementation and integrity

- One application-owned Room instance supplies both repositories. ViewModels own
  loading, immutable observable state, best-effort drafts and explicit saving/errors.
  Compose uses lifecycle-aware collection; storage never runs on the main thread.
  Saved detail/navigation appears only after the transaction returns successfully.
- Six new application tables: programs, independent routines, ordered program-routine
  memberships, ordered routine-exercise occurrences, ordered working-set prescriptions,
  and the minimal singleton Home cursor. UUIDs identify relational rows; exercise
  names are display text. Selected program is derivable from the membership, avoiding
  a second conflicting cursor. RESTRICT foreign keys and unique parent/ordinal indexes
  preserve relationships. No cascade can delete catalogue definitions through plans.
- Domain/repository boundaries validate target ranges, field combinations, nonempty
  routines/sets, occurrence identities and current exercise eligibility. SQL enforces
  PK/NOT NULL/FK/ordinal uniqueness, not all value ranges. Later import/custom writers
  must reuse validation. Existing B-02 preservation/corruption policy remains in place.
- Optional mass uses nullable integer grams; rest uses integer seconds. The metric
  display and exact conversion are centralised. No inferred starting weight, binary
  floating-point storage, progression calculation or performance history is added.
- Routine creation validates the full draft and commits definition, membership,
  occurrences, prescriptions and initial cursor together. Mid-write duplicate-ID
  failure rolls back the entire new graph, including earlier successful inserts.
  Concurrent routine creation allocates distinct ordered membership positions.
